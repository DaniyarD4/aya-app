# Архитектура (черновик для обсуждения, ничего не разрабатываем пока)

## Платформа
Нативное iOS-приложение (SwiftUI). Причины:
- «Премиальный минимализм» на нативном UI получается честнее и дешевле, чем на кроссплатформенном фреймворке.
- Прямой доступ к HealthKit, Apple Watch, локальным уведомлениям, Siri/голосу — всё, что нужно для Rhythm и будущих носимых устройств, нативно на iOS и через костыли — везде ещё.
- Экосистемность (часы, будущий iPad/Mac) естественно растёт из нативного iOS-фундамента.

## Структура фронта (по аналогии с тем, что уже нравится в cyberplatform-front — см. память [[project-cyberplatform-architecture]])
Vertical feature slices, а не классическая MVC-помойка:
```
App/
  Features/
    Rhythm/        — напоминания, чек-листы, стрики
    Flow/          — траты, квесты, награды
    Assistant/     — голос, чат, персона
    Onboarding/
  DesignSystem/     — визуальные примитивы, независимые от бизнес-логики (премиальный минимализм живёт тут)
  Core/             — общие механизмы: уведомления, синк, авторизация (когда появится), i18n (3 языка)
  Infrastructure/   — сеть, локальное хранилище, HealthKit-обвязка
```
Фичи не знают друг о друге напрямую, зависят только от DesignSystem и Core — тот же принцип, что уже работает в cyberplatform-front.

## Локально vs облако — принцип разделения
- **Rhythm-напоминания (обычные, по расписанию)** — планируются **локально** (UNUserNotificationCenter), не требуют сервера и работают офлайн, не жрут батарею на постоянный поллинг. Это сознательный выбор простоты и надёжности (напоминание про лекарства не должно зависеть от того, жив ли бэкенд).
- **Всё, что требует "ума"** (предиктивные напоминания по истории покупок, сезонные чек-листы по погоде, финансовая рефлексия, разговор с ассистентом) — идёт через бэкенд + LLM.
- **Голос (TTS/STT)** — облачный сервис (см. риски по казахскому языку), с текстовым fallback всегда доступным офлайн.

## Бэкенд (нужен уже на MVP ради синка между устройствами и "мозгов" ассистента)
Минимальный, но не игрушечный — на будущее multi-device/family нужно, чтобы данные жили не только на телефоне.
- Тот же стек, что и в cyberplatform-back, если хочется единообразия инструментов (async Python/FastAPI-подобный + Postgres) — **но без RLS-мультиарендности пока**: это personal-app, лишняя сложность для одного пользователя. RLS-паттерн держим в уме на фазу "семейный шеринг/экосистема", не строим заранее.
- LLM для диалогового слоя ассистента (например, Claude API — уже есть опыт работы с Anthropic-стеком).
- Хранилище: траты, история напоминаний, streaks, achievements/rewards — обычные таблицы, без экзотики на старте.

## Данные и приватность
Финансовые данные и данные о здоровье (лекарства, витамины) — чувствительные, даже если пользователь один.
- Шифрование в покое для этих полей — закладываем с первого дня (дешевле сделать сразу, чем переносить позже — тот же принцип, что уже применяется в cyberplatform: "безопасность через архитектуру данных, а не только код").
- Никакой аналитики/трекеров третьих лиц на чувствительных экранах (Flow, здоровье).

## Ассистент-движок
- Персона и тон задаются системным промптом/конфигом персоны (единая точка правды для "характера" ассистента — легко его довести до нужного тона).
- i18n на 3 языка — на уровне контента (строки интерфейса) отдельно от i18n голоса (TTS voice per language) — казахский голос может потребовать отдельного провайдера от русского/английского, архитектура должна такое допускать с самого начала (не завязываться на одного TTS-вендора).

## Что закладываем в архитектуру заранее ради экосистемы (но не строим сейчас)
- Модульность фронта и бэкенда по фичам (уже заложено выше).
- Отдельный namespace для будущего multi-user/family (не строим auth/шеринг сейчас, но модели данных не должны жёстко привязываться к «один пользователь = всё приложение», чтобы потом не переписывать с нуля).
- Абстракция над источником "носимых данных" (HealthKit сейчас, сторонние SDK потом) — один internal-протокол "WearableDataSource", а не прямые вызовы HealthKit по всему коду.

## Технические риски архитектуры (детали — [05-risks-open-questions.md](05-risks-open-questions.md))
- Качество казахского TTS/STT.
- Баланс "локально для надёжности" vs "облачно для ума" — нужно явное решение по каждому виду напоминаний, не смешивать.
- Дизайн системы наград во Flow, чтобы не превратиться в дешёвую геймификацию (риск противоречит ценности "премиальный минимализм").
